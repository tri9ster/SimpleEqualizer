# 失敗・つまずきの記録

1件ずつ残す。新しいものを上に足す。書式は次のとおり。

```
## YYYY-MM-DD: <何が起きたか>

- 症状:
- 原因:
- 対処:
- 教訓:
```

## 2026-10-26: 英語対応で、日本語の Mac でも英語が出るおそれがあった(ビルドしたものを調べて気づいた。利用者の手元では起きていない)

- 症状: 英語対応のあと、ビルドしたアプリを調べると、次の2つが分かった。
  - 開発の地域(Info.plist の `CFBundleDevelopmentRegion`)が `ja` のまま。`Config/Info.plist` に `en` と書いたのに効いていない。
  - 日本語の表(`ja.lproj/Localizable.strings`)がない。`Core/` の部品には `ja.lproj` 自体がない。
  開発の地域を英語にすると、日本語の Mac でも、日本語の表がないので英語の表が使われるおそれがあった。
- 原因:
  - Info.plist を自動で作る設定(`GENERATE_INFOPLIST_FILE`)では、`CFBundleDevelopmentRegion` を `DEVELOPMENT_LANGUAGE` から作り、
    手で書いた値を上書きする。`INFOPLIST_KEY_CFBundleDevelopmentRegion` も効かなかった。
  - 文字列カタログは、元の言語(日本語)の表を作らない。日本語の文言は見出しそのものなので、表がなくても、見出しがそのまま出る想定のため。
- 対処: `Config/Project.xcconfig` で `DEVELOPMENT_LANGUAGE = en` にした。カタログに、日本語の値も、見出しと同じものを明示して入れた
  (これで `ja.lproj` ができる)。どの見出しにも日本語の値があることを、自動テスト(`StringCatalogTests`)で確かめる。
  ビルドしたアプリの表を外から読み、日本語・英語・フランス語の Mac で選ばれる表を確かめた(アプリは起動していない)。
- 教訓: 言語まわりは、ビルドが通っても正しいとは限らない。できたアプリの中身(`*.lproj` と Info.plist)を見て確かめる。

## 2026-10-26: `#expect(throws:)` に、型つきの throws のクロージャを渡すと、コンパイラーが落ちる

- 症状: テストに `#expect(throws: PresetError.duplicateName) { () throws(PresetError) in … }` と書くと、
  `swift test` のビルドで、コンパイラー(`swift-frontend`)が落ちた(Swift 6.4)。
- 原因: コンパイラーの不具合と見ている(機械語を作る段階で落ちた)。中までは調べていない。
- 対処: `do` と `catch` で書き直した。既存のテストは、前から自前の確かめ方(`expect(_:_:)`)を使って、この形を避けていた。
- 教訓: 型つきの throws を確かめるテストは、`do` と `catch` か、既存の確かめ方で書く。

## 2026-10-20: 選択パネルを開くとき・閉じるときに、枠の背景が順に一瞬白く光る

- 症状: 出力先やプリセットの選択パネルを開くとき・閉じるときに、出力先の欄、音量の枠、音質の枠の背景が、順に一瞬だけ白くなった(利用者が気づいた)。
- 原因の切り分け(利用者に見てもらった。1回に1つだけ変えた):
  - 「視差効果を減らす」を入にすると、光らない(このアプリは、そのとき、ぼかし・縮み・タイルが移る動きを止める)。
  - 出力先のパネルを開くとき、移る動きだけをする出力先の欄は光らず、退いていく枠だけが光る → 移る動きは外れる。
  - ぼかしだけを止めると光らない。縮みだけを止めると光る → **原因はぼかし**。
- 原因の見立て(試験の結果に合うが、macOS の中までは確かめていない): ぼかしをかけると、その部分は別の層に描いてから貼り戻される。
  背景の半透明の塗り(`.fill.quaternary` など)は、ふだん後ろのすりガラスの素材と特別な混ぜ方(ヴァイブランシー)で合成されるが、
  別の層では、その混ぜ方が効かず、明るい色のまま描かれる。ぼかしの始めと終わりに切り替わるので、一瞬光る。
  順に光るのは、退かせる動きを枠ごとに 25 ms ずらしているため。
- 対処: 枠と欄の背景だけは、ぼかさずに、薄くする・縮むだけにした(`receding` の `blurs: false`)。中身は、いまどおりぼかす。
- 教訓: 半透明の塗り(ヴァイブランシー)には、ぼかしなど、別の層に描く効果をかけない。見た目の不具合も、1回に1つだけ変えて切り分けると、早く原因にたどり着く。

## 2026-10-20: ⌘Q で終えると、加工中でも確かめずに終わる

- 症状: ポップアップの終了のボタンでは「音は、加工なしの最大音量に戻ります」と確かめるのに、
  ⌘Q(アプリのメニューの「終了」)では、加工中でも確かめずに終わり、音が最大音量に戻った(利用者が気づいた)。
- 原因: 確かめる画面を、ポップアップの終了のボタン(`PopupView.quit`)の中にだけ置いていた。
  ⌘Q は `NSApp.terminate` を直接呼ぶので、このボタンを通らない。
- 対処: 確かめを、アプリの終了の入口(`AppDelegate.applicationShouldTerminate`)へ移した。⌘Q、ボタン、ほかのアプリからの終了の頼みが、すべてここを通る。
  ログアウト、再起動、システム終了のときは、macOS の操作を止めないよう、確かめない(終了の頼みについた理由で見分ける)。
- 教訓: 安全のための確かめは、操作のボタンではなく、すべての道が通る入口に置く。

## 2026-10-15: サンプリング周波数が変わると、音がとぎれる(経路が、作ったときの周波数のままだった)

- 症状: 再生する音源のサンプリング周波数が変わる(48 kHz から 44.1 kHz など)と、音がとぎれる。
  「音声の加工」を切って入れ直すと直る。試作(2026-10-12)のときからの課題。
- 再現の手順: USB SPDIF Adapter で音楽を再生し、「Audio MIDI 設定」で、USB SPDIF Adapter の周波数を 44,100 Hz に変える。
  48,000 Hz に戻すと、何もしなくても直る。
- 原因: 経路の様子を、周波数の変化の知らせを受けたときから、記録に書いて調べた(`research-log.txt`)。
  - 周波数を変えると、出力装置、まとめの装置(集約装置)、音を取り出す口(タップ)の周波数は、44,100 Hz に変わった。
    コールバックの回数も、44,100 Hz として正しい速さになった。
  - 経路(エンジン、リミッター)は、作ったときの 48,000 Hz のまま動いていた。
  - 取り出した音の大きさが、3 秒おきに見ると、0.29 と 0 を行き来していた(48,000 Hz のあいだは、いつも 0 より大きかった)。
    取り出した音が、ところどころ無音になっていて、これが「とぎれる」の正体だった。
  - 48,000 Hz に戻すと、作ったときと同じになり、何もしなくても直った。入れ直すと直るのは、新しい周波数で経路を作り直すためだった。
  - どの部品の食い違いで無音が混ざるのか(タップか、集約装置か)までは、突き止めていない。作り直せば直ることは、確かめた。
- 対処: 出力装置の周波数の変化の知らせを受けたら、その経路を、新しい周波数で作り直す。
  - はじめは、前の経路を片付けてから作る形にした。利用者が確かめ、とぎれなくなった。
    ただ、記録を見ると、片付けてから新しい経路が動くまで、0.7 秒ほどかかっていた。その間は、元の音が、加工なしの元の大きさで出る。
  - `/code-review` の指摘を受けて、新しい経路を先に作ってから、前の経路を片付ける形に変えた。
    前の経路のタップが、新しい経路ができるまで、元の音を消し続ける。利用者が確かめ、コミットの指示を受けた。
  - 記録を見ると、0.7 秒かかっていたのは、片付けではなく、周波数が変わった直後に新しい経路を作る時間だった(ふだんは 0.07 秒)。
  - コミットの前の2回目の `/code-review` で、さらに直した(利用者は、まだ確かめていない)。
    - 2つの経路が重なる間、音量 100 の近くでは、加工した音が二重になり、元の大きさを超えるおそれがある。
      前の経路の音を先に消してから、新しい経路を作る形にした。作り直す間(0.7 秒ほど)は、無音になる。
    - 周波数の知らせを受けたときと、出力先を合わせ直すときで、作り直し方が別々だった。1つ(`rebuildPath`)にまとめた。
    - 知らせを受け始める前に周波数が変わると、気づけなかった。周波数を読む前から、知らせを受けるようにした。
  - 知らせを取りこぼしていても(スリープの間に変わった、など)、作ったときと周波数が違う経路は、作り直す。
- 教訓:
  - 「直ったかどうか」は、記録の数字で確かめる。今回は、取り出した音の大きさが 0 にならなくなったことを、記録で確かめた。
  - 作り直す処理を入れるときは、作り直す間に、何が出るかを測る。片付けてから作る形は、その間、元の音を消すものがなくなる。

## 2026-10-15: アクティビティモニタと、確かめる画面に、仮のアイコンが出る(古いアプリが、同じ識別子で登録されていた)

- 症状: アクティビティモニタと、確かめる画面(ダイアログ)に、用意したアイコンではなく、macOS の仮のアイコンが出た(利用者の指摘)。
  段階2 の確認では、Finder に、用意したアイコンが出ていた。
- 原因:
  - アプリの中のアイコンは、正しかった(アイコンのファイルを画像に戻し、macOS にファイルとして描かせて、確かめた)。
  - macOS に、同じ識別子のアプリが2つ登録されていた。いつも起動している場所(`DerivedData`)のものと、
    Claude が 2026-10-12(試作のころ)に、作業用のフォルダへビルドしたもの。作業用のほうは、アイコンを組み込む前のもので、アイコンがない。
  - 起動しているアプリのアイコンを探すとき、macOS が、アイコンのない古いほうを見ていた、と見立てた。
    古いほうの登録を外して消すと、用意したアイコンが出るようになった(利用者が確かめた)ので、見立ては合っていた。
- 対処: 作業用のフォルダの古いアプリの登録を外し(`lsregister -u`)、消した。アプリのコードは変えていない。
- 教訓:
  - アプリを、いつもの場所(`DerivedData`)以外にビルドしない。同じ識別子のアプリが、macOS に別々に登録され、
    アイコンや許可の扱いが、古いほうに引きずられる。別の場所にビルドしたときは、終わったら登録を外して消す。
  - 調べ方: 登録されている場所は、`lsregister -dump` の `path:` の行で分かる。

## 2026-10-14: ケーブルを抜いて差し直すと、加工なしの音が出る(画面は「加工中」のまま)

- 症状: 段階5 の TICKET-003 のあと、USB SPDIF Adapter のケーブルを抜いて差し直すと、加工なしの音(最大音量)が出た。
  画面は、加工している表示のままだった。「音声の加工」を切って入れ直すと、直った。3 回試して、3 回とも起きた。
- 再現の手順: USB SPDIF Adapter で音楽を再生し、ケーブルを抜く。15 秒ほど待って、差し直す。
- 原因: 経路の様子を記録に書くようにして、差し直しの前後を調べた(`research-log.txt`)。
  - 差し直すと、装置の番号が変わった(101 → 156)。識別子(UID)は同じ。
  - 差し直したあとも、経路のコールバックは呼ばれ続け、集約装置も元に戻っていた(入力 1 本、出力 1 本)。
    ところが、**取り出した音の大きさが、ずっと 0 だった**(ほかのアプリは、その装置へ音を出していた)。
  - つまり、音を取り出す口(タップ)が、前の番号の装置につながったままで、差し直した装置の音を取り出していない。
    取り出していないので、元の音も消えない。アプリは、無音を加工して出し続け、利用者には、加工なしの元の音だけが聞こえる。
  - 「止まっているか」の見張りは、コールバックの回数を見ているので、気づけない。
  - TICKET-003 では、「装置が抜かれても、経路は片付けない。差し直すと、そのまま加工が続く」という作りにしていた。
    TICKET-001 の調査で、そう見えたためである。ただ、調査のときに確かめたのは、「コールバックが呼ばれ続けること」と、
    利用者が聴いた結果だけで、差し直したあとに「音を取り出せているか」は、記録していなかった。
    なぜ、調査のときと、TICKET-003 の最初の確認では、加工された音が出たのかは、分かっていない。
- 対処: 装置が抜かれたら、その経路を片付ける。差し直されたら、新しく作る(タップも、作り直される)。
  気づかないうちに装置の番号が変わっていた場合も、作り直す。
  作り直す間(0.15 秒ほど)は、加工なしの音が出る。差し直すと、いつまでも加工なしの音が出る、いまの動きよりは、ずっとよい。
  直したあと、利用者が、抜き差しを2回確かめた。記録でも、差し直したあとに、音を取り出せていた。
  スリープからの復帰でも、ディスプレイの装置の番号が変わることがあり、同じ直し方で、経路が作り直されていた。
- 教訓:
  - 「動いている」ことを、1つの値(コールバックの回数)だけで判断しない。経路が役に立っているのは、
    「呼ばれている」「音を取り出せている」「形が合っている」の全部がそろっているときである。
  - 調査で「そのまま続く」と見えた動きに頼る作りにするときは、何を確かめて、何を確かめていないかを書いておく。
    今回は、「コールバックが続く」を、「加工が続く」と読み替えていた。
  - 装置を抜いて差し直すと、装置の番号は変わる。番号や、番号につながったもの(タップ)を、差し直しをまたいで持ち続けない。

## 2026-10-14: スリープから復帰すると、「開始に失敗しました(エラー 35)」と出る(スリープの間に、経路を作り直していた)

- 症状: 段階5 の TICKET-003 のあと、Mac をスリープさせ、復帰して音楽を再生すると、ポップアップに
  「音声を加工していません。開始に失敗しました(エラー 35)。」と出た。そのあと、何もしなくても回復し、加工された音が流れた。
  段階4 までは、スリープから復帰しても、何も起きなかった。
- 再現の手順: アプリを動かしたまま、Mac をスリープさせる。10 秒ほどして、復帰させる。
- 原因: TICKET-003 で、「装置があるのに、コールバックが 9 秒ほど呼ばれていない経路は、作り直す」処理を足した。
  スリープに入ると、コールバックは止まるが、アプリは、しばらく(10 秒ほど)動き続ける。装置も、一覧に残っている。
  そのため、スリープに入って約 10 秒後に、動いていた経路を片付けて、作り直そうとしていた。
  スリープの間は、装置を始められず、エラー 35 になる。始めようとする呼び出しは、6 秒ほど戻らなかった(その間、アプリが固まる)。
  記録(`research-log.txt`)に、「スリープに入る」→ 4 秒後「コールバックが呼ばれなくなった」→ 10 秒後「経路が動いていないので、作り直す」→
  「経路を作れなかった: 開始に失敗しました(エラー 35)」と、順に残っていた。
  経路を持ったままにしておけば、復帰のあと、何もしなくても、コールバックは、また呼ばれる(TICKET-001 の調査で確かめてあった)。
  つまり、動いていたものを、わざわざ壊していた。復帰の直後に、加工なしの音が出るおそれもあった。
- 対処:
  - 動いていない経路を、自動で作り直す処理を、取り除いた。この処理は、「差し直したあとに経路が戻らない場合」への備えとして足したが、
    その場合は、一度も起きていない(調査でも、利用者の確認でも、差し直すと、そのまま加工が続いた)。
  - スリープに入る知らせから、復帰の知らせまでの間は、経路を作ることも、片付けることもしない。
    復帰して 2 秒後に、出力先を合わせ直す(スリープの間に、出力先が変わっていた場合のため)。
  - 止まっていることの表示(メニューバーのアイコン)は、これまでどおり出す。戻らないときは、利用者が「音声の加工」を入れ直せる。
- 教訓:
  - **起きたことのない場合への備えを、確かめずに足さない。** 今回の処理は、`/code-review` の指摘(差し直したあとに戻らなかったら?)を受けて、
    起きるかどうかを確かめないまま足した。その備えが、実際に起きている場面(スリープ)を壊した。
    指摘が「起きうる」と言っている場合は、まず、起きるかを確かめる。確かめられないなら、足さずに、`TODO.md`(いまは `private/TODO.md`)に書く。
  - 「コールバックが呼ばれていない」は、異常とは限らない。スリープの間は、呼ばれないのが正しい。
    調査(TICKET-001)の記録に、スリープの間はコールバックが止まることが残っていたのに、作りに生かせなかった。
  - 自動で直そうとする処理は、直す対象が、ほんとうに壊れているかを、見分けられるときだけ入れる。

## 2026-10-14: 出力先を切り替えると、「音量が大きいため、音を抑えています」と出る(別の経路の回数と比べていた)

- 症状: 段階5 の TICKET-003 の確認で、出力先を USB SPDIF Adapter に切り替えるたびに、イコライザーのウィンドウに
  「音量が大きいため、音を抑えています」と出た。ディスプレイのスピーカーに切り替えたときにも、出ることがあった。2 秒ほどで消える。
- 再現の手順: イコライザーのウィンドウを開いたまま、出力先を切り替える。切り替え先が、前に1回でもリミッターが働いたことのある出力先だと、出る。
- 原因: 表示は、「リミッターが抑えていた回の数が、前に見たときより増えたか」で決めていた。
  TICKET-003 で、経路を出力先ごとに持つようにし、回数も経路ごとになった。出力先が変わると、読む回数が、別の経路のものに変わる。
  切り替え先の経路の回数のほうが大きいと、「増えた」と判断して、表示していた。
  実際にリミッターが働いたわけではない(切り替えた瞬間に、音が抑えられたわけではない)。
- 対処: 表示の判断を `Core/` の `LimiterIndicator` に移し、どの出力先の回数かをあわせて受け取るようにした。
  出力先が変わったときは、比べ直す(別の経路の回数とは比べない)。テストを先に書いた。
- 教訓:
  - 1つだったものを複数にしたとき(経路を1本から、出力先ごとに)は、「前の値と比べる」処理を、全部見直す。
    比べる相手が、同じものの前の値とは限らなくなる。今回は、見張り(止まっていないか)の数え直しは直したのに、
    リミッターの表示を見落とした。
  - 画面の側に書いた判断は、テストがないので、こういう見落としに気づけない。判断は `Core/` に置く。
  - 切り替えた瞬間に、実際にリミッターが働いていないかは、記録で確かめる(経路ごとの回数を、切り替えのたびに記録に書くようにした)。

## 2026-10-12: CPU 使用率が目標の倍以上(コールバックの中の `for ... in` が実行時の処理を呼んでいた)

- 症状: TICKET-003 の確認で、再生中の CPU 使用率が 8% 前後だった(目標は 3% 以下)。音は正常に出ていた。
- 再現の手順: Debug のビルドで起動し、「開始」を押して音を再生し、アクティビティモニタを見る。
- 原因: 音声のコールバックの中で、サンプルごとの繰り返しを `for frame in 0..<frames` と書いていた。
  最適化なしのビルドでは、この書き方は1回ごとに Swift の実行時の処理(型の情報を探す処理)を呼ぶ。
  その処理はロックを使うので、「コールバックの中でロックを使わない」というルールにも反していた。
  `sample` コマンドで調べると、音声のスレッドの時間の 5.8% がここに使われていた。
- 対処: 繰り返しを `while` に書き直した。最大値の計算も、汎用の関数(`max`、`abs`)を使わない形にした。
  機械語を調べ、コールバックが呼ぶ関数が、バッファの読み取りと `memset` だけになったことを確かめた。
  直したあと、利用者が測り直して 2.4% になった。
- 教訓:
  - コールバックの中では、`for ... in`、`max`、`abs` などの汎用の書き方を避け、`while` と単純な計算で書く。
    最適化ありのビルドでは消えるが、ふだん試すのは最適化なしのビルドである。
  - ソースを読んでも、コールバックが裏で何を呼ぶかは分からない。機械語で呼び出し先を一覧して確かめる。

    ```bash
    otool -tV <.app の中の SimpleEqualizer.debug.dylib> \
      | awk '/^[^ \t].*:$/{fn=$0; next} /\tbl\t/{print fn"\t"$NF}' | grep render | xcrun swift-demangle
    ```

  - 負荷が高いときは、推測する前に `sample <プロセス番号> 5` で、どのスレッドのどの関数が時間を使っているかを見る。

## 2026-10-12: 「開始」を押すとアプリが落ちる(音声のコールバックがメインスレッド専用とみなされた)

- 症状: TICKET-002 の試作で「開始」を押すと、すぐにアプリが落ちた。音は元の経路で出たままだった。
  クラッシュの記録では、音声のスレッド(`com.apple.audio.IOThread.client`)が
  `_swift_task_checkIsolatedSwift` → `dispatch_assert_queue` で止まっていた。
- 再現の手順: 出力先を USB SPDIF Adapter にして音を再生し、アプリを起動して「開始」を押す。
- 原因: 音声のコールバック(クロージャ)を、`@MainActor` をつけたクラスのメソッドの中に書いていた。
  Swift 6 では、そこに書いたクロージャもメインスレッド専用とみなされ、
  呼ばれたときに「メインスレッドで動いているか」を調べる検査が自動で入る。
  Core Audio はコールバックを音声のスレッドで呼ぶので、最初の1回で検査に引っかかって落ちた。
  ビルドではエラーも警告も出なかった(C の API に渡すブロックは、どのスレッドで呼ばれるかの情報を持たないため)。
- 対処: コールバックを、メインスレッド専用ではない関数(`nonisolated static func makeIOBlock`)の中で作るようにした。
  直したあと、できたプログラムの機械語を調べ、コールバックの中に検査の呼び出しが残っていないことを確かめた。
  そのあと利用者が試し、落ちずに音が出ることを確かめた。
- 教訓:
  - 音声のスレッドで呼ばれるクロージャは、`@MainActor` のついた型のメソッドの中に書かない。
    `nonisolated` の関数か、型の外の関数の中で作る。
  - この種の誤りは、ビルドでも `/code-review` でも見つからなかった。
    音声のコールバックを足したり動かしたりしたときは、利用者に試してもらう前に、機械語に検査が入っていないかを調べる。

    ```bash
    otool -tV <.app の中の SimpleEqualizer.debug.dylib> | grep -E "isCurrentExecutor|checkIsolated"
    ```

    出てきた行が、音声のスレッドで動く関数の中にないことを確かめる。
  - 落ちたときに音が元の経路に戻ることは、この失敗で1回確かめられた(「読み取っている間だけ元の音を消す」設定の効果)。
