## 2. 処理の流れ

### 2.1 いまの経路

```
各アプリの音 → タップ(元の音は消す) → エンジン(イコライザー → ラウドネス) → 音量 → リミッター → USB SPDIF Adapter → SONOS Ray
```

イコライザーの値は、ウィンドウで変える。ラウドネスは、音量と強さから決めた補正量をエンジンへ伝える。

経路は、出力先1つにつき、1つ作る(下の「2.5 出力先に合わせる」)。1つの経路の作り方は、次のとおり。

1. 出力先の装置を受け取る(装置は、`AppModel` が、いまある出力先の中から決める)。
2. タップを作る。対象は、この出力装置に出ている音だけ。自分自身のプロセスは外す。
   アプリが読み取っている間だけ、元の音が消える。
3. 集約装置を作る。出力装置とタップを1つにまとめたもので、ほかのアプリからは見えない。
   入力(タップ)と出力がそれぞれ1本でなければ、開始しない。
4. エンジンを作って始め、C のコールバックにつなぐ。作れないときは、開始しない。
5. 集約装置に、C のコールバック(`seq_io_proc`)を登録する。取り出した音をエンジンに通し、倍率を掛け、リミッターを通して出す。
6. 停止のときは、音をなめらかに消し、消えきったのを確かめてから、コールバック、集約装置、タップ、エンジンの順に片付ける。

受け持ちの分け方:

| 部分 | 言語 | 場所 |
| --- | --- | --- |
| 音声のスレッドで動く関数と、画面との受け渡しの値 | C | `Core/Sources/SimpleEqualizerAudio/` |
| エンジンを C のコールバックにつなぐ関数 | Objective-C | `Core/Sources/SimpleEqualizerAudio/seq_engine.m` |
| エンジンの組み立てと、値の設定 | Swift | `Core/Sources/SimpleEqualizerEngine/` |
| 組み立て(装置、タップ、集約装置、登録、片付け) | Swift | `SimpleEqualizer/AudioPath.swift` |
| 音量の換算、状態の保存 | Swift | `Core/Sources/SimpleEqualizerCore/` |

画面とコールバックの間の値(目標の倍率、取り出した音の大きさ、回数)は、ロックを使わない方法(C のアトミック)で受け渡す。

コールバックの決まり:

- 倍率は 0 以上 1 以下(元の音量を超えない)。C の側で丸める。
- 倍率は、1回の呼び出しの中でなめらかに変える。開始のときは 0 から上げる。
- 形が合わないときは無音を出す。数でない値や無限大のサンプルは、無音に置き換える。
- 最後にリミッターを通す。音量を掛けたあとの音がフルスケールを超えるフレームでは、全チャンネルの倍率をすぐに下げ、
  超えなくなったらゆっくり戻す。超えておらず、倍率も戻りきっている回(ほとんどの回)は、通さない。

### 2.2 起動から終了まで

1. 起動: `state.json` を読む。読めなかったときは初期値で始め、理由を覚えておく。
2. 加工を自動で始める。出力先が分かった時点で、その出力先について覚えている音量と消音から、はじめの倍率を決める。
   音は、倍率 0 からなめらかに上がる。始められないときは、音声に触らず、理由をポップアップに出す。
3. 音量や消音を変えると、すぐに音声の経路へ伝え、0.5 秒後にまとめて保存する。
4. 3 秒おきに、コールバックが呼ばれ続けているかを確かめる。止まっていたら、メニューバーのアイコンを変える。
   あわせて、音を取り出せているかを確かめる(ほかのアプリが音を出しているのに、一度も音を受け取っていない状態が続いたら、
   「システム音声の録音」の許可がないと疑い、案内の画面を出す)。
5. 終了: 加工中なら、確かめてから終える(`AppDelegate.applicationShouldTerminate`。⌘Q も、ポップアップのボタンも、ここを通る)。
   保存し、音をなめらかに消してから、音声の経路を片付ける。

### 2.3 エンジンを通すところ

- エンジン(`AVAudioEngine`)は「手動レンダリング(リアルタイム)」で動かす。装置は持たず、C のコールバックが、その中から呼ぶ。
- 取り出した音は左右が交互に並ぶ。C の側でチャンネル別に並べ替えてエンジンに渡し、受け取った音を交互に並べ直す。
  並べ替えの置き場は、エンジンをつなぐときに確保する。
- エンジンを通せなかった回(エンジンが断った、フレーム数が置き場の 4096 を超えた、チャンネル数が違う)は、
  取り出した音をそのまま使う。無音にはしない。音量とリミッターは、どちらの場合も掛かる。回数は数えてある。
- エンジンをつなぐ・外すのは、コールバックが止まっている間だけ。
- 音声のスレッドで動く自分のコードは、C の関数と、C の関数を1つ呼ぶだけのブロック(`seq_engine.m`)である。
- 調べた内容は `research/AVAudioEngine_Tap.md`、試作のコードは `archive/20261012_prototype/` にある。

### 2.5 出力先に合わせる(段階5 の TICKET-003)

- 経路を持つ出力先は、「いまの出力先」と、「音量を変えられない出力先の全部」(扱える形のものだけ)。
  音量を変えられない出力先の経路を、いまの出力先でないあいだも持ったままにするのは、戻した瞬間に、
  加工なしの最大音量が出ないようにするため(経路を作り直すと、0.15 秒ほどかかる。`research/OutputDevices_Survey.md`)。
- 出力先の変化(いまの出力先が変わった、装置が増えた・減った)の知らせを受けるたびに、いまある出力先を読み直し、
  足りない経路を作り、要らない経路を片付ける。何度呼んでも同じ結果になるように作ってある
  (知らせは、同じものが続けて来る。アプリが自分で集約装置を作ったり消したりしたときにも来る)。
- 装置が抜かれたら、その経路を片付ける。差し直されたら、新しく作る。差し直すと、装置の番号が変わり、
  前の経路は、コールバックが呼ばれていても、音を取り出せなくなるため(`failures.md` の 2026-10-14)。
- ポップアップのプルダウンで出力先を選ぶと、`AppModel.selectOutput` が macOS の出力先を書き換えるだけで、経路には触らない。
  そのあとは、macOS のメニューで切り替えたときと同じく、知らせを受けて合わせる。切り替え方ごとに別の道を作らないため。
- プルダウンに出すのは、macOS の出力先になれる装置(`kAudioDevicePropertyDeviceCanBeDefaultDevice`)と、いまの出力先。
  顔ぶれを macOS のサウンドの一覧に合わせるため。読めなかった装置は、なれるものとして扱う。
  加工の対象は、これでは絞らない(いまの出力先が、なれないと答えても、加工を止めないため)。
- スリープの間は、経路を作ることも、片付けることもしない。持ったままの経路は、復帰すると、何もしなくても、また動き出す。
  復帰して 2 秒たってから、経路に触ってよいことにして、出力先を合わせ直す。スリープの間は、「止まっている」とも判断しない。
- 動いていない経路を、自動で作り直すことは、しない(いったん入れたが、スリープの間に、動いていた経路を壊したので、取り除いた。
  `failures.md` の 2026-10-14)。止まっていることは、メニューバーのアイコンで知らせる。
- イコライザーは、全部の経路に同じ値を掛ける。倍率とラウドネスの補正量は、出力先ごとに、
  覚えている音量と、出力先の性質(`Core/` の `OutputDevice`)から決める。
- 画面の音量と消音は、いまの出力先のものを出す。見張り(止まっていないか、音を取り出せているか)も、いまの出力先の経路について行う。

### 2.4 完成時の予定(仕様書 7章)

```
各アプリの音 → タップ(元の音は消す) → イコライザー → ラウドネス → 音量 → リミッター → USB SPDIF Adapter → SONOS Ray
```

## 3. エンジンとコールバックのつなぎ方(Objective-C を使う理由)

2026-10-12、段階3 の TICKET-003 で決めた。利用者から理由を聞かれ、記録に残すことになった。

### なぜ C だけで済まないか

エンジン(`AVAudioEngine`)は、Objective-C で作られた部品である。エンジンとの受け渡しは2つあり、
どちらも Objective-C の呼び出し方でしか行えない。C には、Objective-C の部品を呼ぶ書き方がない。

1. エンジンから「加工の入口」(`manualRenderingBlock`)を受け取る。
2. エンジンへ「加工する音の受け取り口」(入力のブロック)を渡す。

### 比べた書き方

| 書き方 | 内容 | 問題 |
| --- | --- | --- |
| Swift で行う | 組み立てのコードから、そのまま呼ぶ | 入口も受け取り口も「ブロック」という形の関数で、Swift はブロックを Swift の関数の形に包み直して扱う。C に渡すと、もう一度ブロックの形に包み直される。C が入口を呼ぶたびに、Swift が自動で作った変換のコードを通り、それが音声のスレッドで動く |
| C で行う | Objective-C の仕組み(実行時の関数)を、C から手作業で呼ぶ | 書けるが、コンパイラが型の誤りを調べない。誤ると、ビルドは通って実行時に落ちる |
| Objective-C で行う(採用) | `seq_engine.m` の関数2つ | 言語が1つ増える |

- Objective-C は、ブロックをそのままの形で扱う。包み直しがないので、C が呼ぶのは、エンジンの入口そのものになる。
- 2 の受け取り口には、macOS 27 で、音声のスレッド向けの渡し方(`setRealtimeSafeManualRenderingInputPCMFormat`)が足された。
  Apple は、これに「Swift からは使えない」という指定をつけている(Swift からは呼べない)。Objective-C からは呼べるので、これを使う。

### 確かめたことと、確かめていないこと

- 確かめた(機械語): C のコールバック(`render_through_engine`)は、エンジンの入口を直接呼ぶ。
  受け取り口のブロックが呼ぶのは、C の関数(`seq_render_state_engine_input`)1つだけである。
- 確かめていない: Swift で行った場合に、変換のコードが実際に害になるか。Swift 版を作って調べてはいない。
  小さなコードなので、害がない可能性もある。
- それでも Objective-C にした理由: 試作での2回のつまずき(`failures.md`)は、どちらも
  「Swift が自動で入れた、ソースからは見えないコード」が原因だった。同じ種類のものを、音声のスレッドに置かない。

### 範囲

- Objective-C で書くのは、`seq_engine.m` の関数2つ(入力をつなぐ、入口を C へ渡す)だけ。どちらも音声のスレッドでは動かない。
- 音声のスレッドで動く Objective-C のコードは、C の関数を1つ呼ぶだけのブロック1つ。
- Xcode の標準の範囲で、外部ライブラリは使っていない。
- `seq_engine.m` を直したら、機械語を調べる(`failures.md` の手順)。

## 5. 設計判断

- **ポップアップの枠と欄の背景(半透明の塗り)は、ぼかさない**: 選択パネルを開くとき、ほかの中身を退かせる動き(`PopupView` の `receding`)で、
  背景までぼかすと、ぼかしの始めと終わりに、背景が一瞬白く光った(`failures.md` の 2026-10-20)。
  背景には `blurs: false` を渡し、薄くする・縮むだけにする。枠ごと退かせるときは `recedingCard` を使う。

- **案A(Core Audio のプロセスタップ)を選んだ**: ドライバーなどの追加インストールなしで、システム全体の音を加工できるため。
  仮想オーディオ装置(案B)は、ドライバーの導入と保守が重い。比較は仕様書の3章にある。
- **音量をイコライザーの後ろに置く**: 音量を下げている間は、イコライザーで増幅しても上限を超えない。
  リミッターが働くのは音量が最大付近のときだけになる。
- **Xcode のプロジェクトとして作る**: 許可(システム音声の録音、アクセシビリティ)が `.app` と署名にひもづくため。
  署名がビルドのたびに変わると、許可を毎回出し直すことになる。
- **開発用の証明書で署名する**: その場かぎりの署名は、ビルドのたびに識別情報が変わる。
  証明書で署名すると、作り直しても同じアプリとして扱われる(2回のビルドで識別情報が同じことを確認した)。
- **アプリの識別子と署名の設定を Git の外に置く**: 識別子に個人の名前が入るため。
  `Config/Project.xcconfig` が `Config/Signing.xcconfig` を読み込む。このファイルがないとビルドできない。
- **プロジェクトのファイルを手で書いた**: 外部のツールを足さないため。
  フォルダを自動で取り込む形式(Xcode 16 以降)を使い、ファイルを足すたびに書き直さずに済むようにした。
- **サンドボックスを使わない**: 配布しないため。タップと音量キーの扱いが単純になる。
- **試作の最初の経路では `AVAudioEngine` を使わない**: 部品を減らし、動かないときに原因を切り分けやすくするため。
  `AVAudioEngine` に通せるかは TICKET-004 で確かめる。
- **タップの対象を出力装置で絞る**: システム全体を対象にすると、ほかの装置に出ている音まで消してしまう。
- **読み取っている間だけ元の音を消す設定にする**: アプリが止まったり落ちたりしたときに、無音のままにならない。
  そのかわり、止まると元の音が最大音量で出る。
- **安全側に倒して開始しない条件**: 装置が見つからない、同じ名前の装置が複数ある、自分のプロセスを外せない、
  取り出した音が 32 ビットの浮動小数点でない。
- **倍率は、コールバック1回の中でなめらかに変える**: 急に変えると雑音が出る。開始のときは 0 から上げる。
- **エンジンは、自分のコールバックの中から呼ぶ(手動レンダリング)**: エンジンに装置を持たせる方式より遅れが増えず、
  エンジンが失敗した回に加工なしの音へ切り替えられる。
- **エンジンの中はチャンネル別の標準の形式にそろえる**: 加工の部品がこの形式を前提にしているため。
  並べ替えは自分で行い、置き場は開始のときに確保する。
- **音声のコールバックは C で書く(段階2 から)**: Apple が、Swift を音声のリアルタイムのスレッドで使うことに
  対応していないと注記している。試作でも、Swift がコールバックの中に、ビルドでは分からない処理
  (スレッドの検査、ロックを使う実行時の処理)を入れたことによるつまずきが2件あった(`failures.md`)。
  C にするのは音声のスレッドで動く部分だけで、組み立て、設定、画面は Swift のままにする。
  試作のコードは Swift で書いてあり、機械語を調べる確認で安全を確かめている。
- **音声に触らない処理を、別のパッケージ(`Core/`)に分ける**: テストを、アプリを起動せずに動かすため。
  アプリを起動する形のテストは、起動のたびに音声に触るおそれがある。パッケージなら `swift test` だけで動く。
- **音量の対応は3乗**: 音量を 0〜1 に直した値の3乗を倍率にする。
  試作の対応(−50〜0 dB の直線)は、利用者が使ってみて「小さい側が細かすぎる」と感じた。
  3乗は、小さい側が早く無音に近づき、0 で自然に無音になる。初期値の 30 での大きさは試作とほぼ同じ(3.6 dB 大きい)。
- **状態は、出力先(装置の UID)ごとに持つ**: 音量と消音を出力先ごとに覚えるため(仕様書 4.1)。
  名前ではなく UID を使うのは、同じ名前の装置を見分けるため。
- **読めなかったファイルを、初期値で上書きしない**: 読み込みの結果に種類を持たせ、保存してよいかを返す。
  あるのに読めないファイル、新しい版のファイル、別名にできなかった壊れたファイルは、上書きしない。
  外付けドライブの不調などで一時的に読めなかっただけの設定を、消さないため。
- **ファイルの中の範囲外の音量は、近い端ではなく初期値にする**: 壊れた値(たとえば 999)を 100 に丸めると、最大音量で音が出る。
- **C のコードを、アプリの中ではなく `Core/` パッケージに置く**: Swift から使うためのヘッダーの設定が要らない。
  それ以上に、コールバックの計算(倍率、なめらかな変化、形が合わないときの無音)を、音を出さずに自動テストで確かめられる。
- **Core Audio には、C の関数を直接登録する**: Swift のクロージャを挟まない。
  試作でのつまずき(スレッドの検査が入ってアプリが落ちた)が、仕組みとして起きなくなる。
- **「音をなめらかに消す」は、C の側が持つ**: 止めるときに目標の倍率を 0 に書き換える形だと、
  同じ値を Swift と C の2か所で持ち、書き戻しを忘れると次の開始が無音になる。
- **入力と出力が1本ずつの装置だけを扱う**: 出力が複数本の装置では、コールバックが、タップではない入力を出力へ写すおそれがある。
  いろいろな出力先を扱う段階5 で、タップの入力を確実に選ぶ形に直す。
- **加工が止まっていないかは、いつも確かめ、メニューバーのアイコンで知らせる**: 止まると、元の音が最大音量で出る。
  常駐のアプリは、ふだんポップアップを開かないので、開いている間だけの確かめでは気づけない。
- **音が最大音量に戻る操作(終了、加工を切る)は、確かめてから行う**: 押し間違いで大きな音を出さないため。
  加工を切る操作は、スイッチではなくボタンにした。確かめる画面で取り消したときに、表示だけが変わるのを防ぐ。
- **保存は、変更の 0.5 秒後にまとめて行う**: スライダーを動かしている間、動かすたびにファイルへ書かないため。
- **アプリ用のアイコンは、スクリプトで SVG から書き出す**: 外部のツールを入れずに、作り直せるようにするため。
  書き出した PNG も Git に入れる(ビルドのたびに書き出さない。ビルドを単純に保つ)。
- **音量の値を2つ持つ(初めて使う出力先は 100、保存してあった値が使えないときは 30)**:
  初めて使う出力先を 100 にしても、アプリを使う前より大きくはならない。
  いっぽう、前に小さくして使っていた設定が壊れたときに 100 にすると、急に大きな音が出る。
  設定のファイルがあったのに全体が読めなかったときも、同じ理由で 30 にする(`AppState.recovered`)。
- **許可がないことは、状況から判断する**: macOS には、「システム音声の録音」の許可の状態をアプリから調べる公開の方法がない。
  許可がなくても、タップも集約装置も作れて、コールバックも呼ばれる。
  「ほかのアプリが音を出しているのに、一度も音を受け取っていない」ことを手がかりにする。
  まちがって疑う場合がある(無音のまま出力を動かしているアプリ)ので、案内は起動してから1回だけにする。
- **リミッターは C で自分で書き、音量の後ろに置く**: 音量は C のコールバックが掛けているので、その後ろに置くには C の側が素直である。
  macOS に入っている部品を使うと、音量もエンジンの中へ移すことになり、段階2 で確かめた音量の変化を作り直すことになる。
  自分で書くと、「どんな入力でも出力が上限を超えない」ことを、音を出さずに自動テストで確かめられる。
- **リミッターの上限はフルスケールちょうど**: 少しでも下にすると、増幅していなくても、フルスケールまで使っている音源で働き、
  元の音が変わる。
- **リミッターが下げる倍率に下限(−40 dB)を置く**: 壊れた大きな値が1サンプル混ざっただけで、しばらく無音になるのを防ぐ。
  下限で収まらない分は、±1.0 で切り落とす。
- **保存してあったイコライザーの値は、1つでも壊れていたら全部を使わない**: 壊れた値を近い端(+10 dB)に丸めたり、
  読めた分だけ使ったりすると、意図しない増幅になる。音量の「壊れた値で大きな音を出さない」と同じ考え方。
- **書いてあるのに読めない入・切は、切にする**: 「入」にすると、切にしていた増幅が、起動時に勝手に入る。
  項目がないとき(段階2 のファイル)だけ、初期値(イコライザーは入でフラット)にする。
- **ラウドネスの補正は、いつも音量による減衰より小さくする**: 上限(強さ 100 で +15 dB)に達する減衰(18 dB)を、上限より大きくしてある。
  上限をこれ以上上げるときは、18 dB を超えないようにする(超えると、ラウドネスだけで元の音量を超える)。
  ラウドネスだけで、音が元の音量を超えることはない。値を変えるときも、この条件をテストで確かめる。
- **エンジンと C のコールバックは、Objective-C でつなぐ**: Swift から渡すと、Swift のクロージャが間に入り、
  音声のスレッドで Swift のコードが動く。Objective-C なら、エンジンの入口(ブロック)をそのまま C に渡せる。
  macOS 27 で足された、音声のスレッド向けの入力の入口も、Swift からは使えず、Objective-C からは使える。
  比べた書き方と、確かめていないことは、3章にある。
- **エンジンの組み立てを `Core/` パッケージに置く**: 手動レンダリングのエンジンは装置に触らない。
  本物のエンジンを C のコールバックにつないだ形で、音を出さずに、イコライザーの効き方まで自動テストで確かめられる。
- **エンジンを通せなかった回は、無音にせず、取り出した音をそのまま使う**: 設定を変えた瞬間に音がとぎれるのを避ける。
  音量とリミッターはその回にも掛かるので、音が元の音量を超えることはない。
- **扱えない高さのバンドは、上限に寄せずに使わない**: 寄せると、サンプリング周波数が低い装置で複数のバンドが重なり、
  増幅が足し合わされる。
- **イコライザーのスライダーは、引いた長さのぶんだけ動かす**: 押した場所へ値を飛ばすと、
  ウィンドウを手前に出そうとして押しただけで、急に +10 dB になるおそれがある。
- **イコライザーの値は、加工を始めるたびに、音を出し始める前にエンジンへ渡す**: エンジンは、始めるたびに作り直され、0 dB で始まる。
- **リミッターの様子は、イコライザーのウィンドウを開いている間だけ調べる**: 常駐のアプリなので、ふだんは余計な処理を動かさない。
  表示は、最後に抑えたときから 2 秒保つ(保たないと、音の山に合わせて点滅する)。
- **ラウドネスの補正量は、出力先の設定(`OutputSettings`)から決める**: 音に掛ける倍率と同じ音量を使うため。
  別々に決めると、壊れた音量のときに、音と補正が別の音量を前提にしてしまう。消音は見ない(消音を解いたときに、そのままの音で戻る)。
- **ラウドネスは、強さ(0〜100)と、入・切のスイッチの両方で持つ**: 強さは、利用者が聴いて、効き具合を自分で変えたいと要望した。
  ちょうどよい強さは、音源や出力先によって変わるので、Claude が値を決め直して聴いてもらうより、利用者が動かせるほうが早い。
  はじめは強さ 0 を「切」とし、入・切は持たなかった(「入なのに強さ 0」の組み合わせを避けるため)。
  2026-10-18 に、強さを覚えたまま聴き比べたいという要望で、スイッチを足した。音に掛ける強さは `AppState.effectiveLoudnessAmount`
  (切なら 0)の1か所で決め、「入なのに強さ 0」は、効かないだけで、困らないものとして扱う。
- **ラウドネスの補正は、音量 50 あたりで上限に達し、それより下げても増やさない**: 利用者が聴いて、
  「小さい音量で効きすぎる、中くらいの音量で弱い」と感じたため。
- **プリセットは、一覧(`PresetLibrary`)を通してだけ作り、書き換える**: 名前の決まり(空でない、30 文字まで、重ならない)と、
  「フラット」を変えられないことを、1か所で守るため。アプリの側からは、プリセットを直接作れない。
- **プリセットの名前は、整えてから調べて保存する**: 空白の数や、見えない文字だけが違う名前は、一覧では見分けがつかない。
  「同じ名前は作れない」という決まりが、見た目のとおりに働くようにする。
- **一部が壊れた `presets.json` は、読み込んだその場で写しを残し、読めた分で書き直す**: 壊れた1件を、次の保存で黙って消さないため。
  保存のときに写しを残す形だと、「写しを残したか」を覚えておく必要があり、残し忘れると消える。
  書き直すのは、起動のたびに写しが増えないようにするため。写しを残せないときは、書き直さず、上書きもさせない。
- **プリセットの一覧がないファイルは、「0 件のファイル」ではなく、壊れたファイルとして扱う**: 項目の名前が変わったり、
  別のファイルと入れ替わったりしたときに、読めたことにすると、次の保存で元の中身が残らずに消える。
- **版の番号が整数として読めないファイルには、触らない**: 新しい版の書き方かもしれない。壊れたファイルとして別名に移すと、
  新しい版のアプリが、自分のファイルを見失う。
- **ファイルを読む手順(あるか、読めるか、版、壊れていたら別名)は、`state.json` と `presets.json` で共通にする**: 同じ決まりを2か所に書くと、片方だけ直して動きがずれる。
- **プリセットの一覧は、変えるたびにすぐ保存する**: 音量などは 0.5 秒後にまとめて保存するが、プリセットは、作りためた設定で、
  変える回数も少ない。書けなかったときは、その場で知らせ、次にプリセットを変えたときと、終了のときに、もう一度試す。
- **プリセットのファイルを読めなかった起動では、プリセットを変えさせず、選んでいたプリセットの記録も書き換えない**:
  読めなかったのが一時的なもの(ドライブの不調など)なら、次の起動で、元の一覧と選択に戻れる。
- **選んでいるプリセット(`selectedPresetID`)と、いまの値(`equalizer`)を、別々に持つ**: いまの値が、選んでいるプリセットの値と
  違うことが「保存していない変更」(`*`)である。起動し直しても、変更は残る。
- **プリセットを削除したあとは、「フラット」に切り替える(値も 0 dB にする)**: 値を残して「フラット *」にする案を、いったん作った
  (音を下げる設定のプリセットを消した瞬間に、音が大きくなるのを防ぐため)。利用者が見て、消したのに `*` が出るのは
  状況が分かりにくいと判断した。音が大きくなりうることは、確かめる画面で伝える。
- **確かめる画面の「進める」ボタンは、Return キーで押せないようにする**: 元に戻せない操作や、音が最大音量に戻る操作が、
  押したはずみで進まないようにする。ダイアログは、1つの作り(`Dialogs.confirm`)にまとめてある。
  ポップアップの中の確かめるカード(`PopupView` の `ConfirmCard`)も、同じ決まりにする(進めるボタンを既定のボタンにしない。キャンセルに Esc)。
- **ポップアップの操作で確かめるときは、ポップアップの中のカードにする**(2026-11-07、利用者の指示): 画面の真ん中のダイアログでは、目線の移動が大きい。
  カードは、選択パネルと同じく、ほかの中身を退かせて(`receding`)、その上に重ねる。押した場所の近くに出す(`Confirmation.edge`。上と下で重ねる場所を分け、閉じる動きが別の場所へ飛ばないようにする)。
  ポップアップを閉じたら、カードも閉じる(キャンセル)。確かめる理由がなくなったら(加工が自動で止まった、など)、何もせずに閉じる。
  ⌘Q とイコライザーのウィンドウの操作は、ポップアップが閉じていることがあるので、ダイアログのまま。
  ✕ のボタンも、終了の入口(`AppDelegate.applicationShouldTerminate`)を通す。カードで確かめたときは、入口に1回だけ使える印を渡し、
  ダイアログで二度確かめない(印を残すと、取り消されたあとの ⌘Q で、確かめずに終わるおそれがある)。
  入口がダイアログを出すときは、知らせ(`AppDelegate.willConfirmQuit`)でポップアップのカードを閉じる(カードとダイアログを同時に出さない)。
  プリセットの選択パネルで、保存していない変更があるまま選んだときは、パネルをそのままカードに切り替える(`switchPanel`)。
  ほかの中身を退かせる状態(`isReceded`)は、パネルとカードで分け合うので、片方を閉じても、もう片方を出していれば退いたままにする。
  確かめる理由がなくなったかは、場面ごとに1か所で決める(`closeConfirmationIfUnneeded`)。
- **画面をはさむ操作は、画面を出す前に、相手のプリセットを決めておく**: 画面を出している間に選択が変わっても、別のプリセットを変えない。
- **音量キーは、加工している間だけ受け取る**: 加工していないときは、アプリは音量を変えられない。
  キーを受け取ってしまうと、macOS の音量も変わらず、キーが何もしなくなる。
- **音量キーの受け取りは、メインスレッドで行い、すぐに終える**: 遅いと、macOS が受け取りを止める。止められたときは、入れ直す。
  アプリが落ちると、受け取りは自動で外れ、キーは macOS に戻る。
- **「アクセシビリティ」の許可は、見張りのたびに確かめる**: 許可は、利用者がシステム設定で、アプリの外から変える。
  出たら受け取りを始め、取り消されたら外す。アプリを起動し直さなくてよい。
- **音量キーで動かす量は、刻み(1/16)の上へそろえる**: いまの音量に足し引きするだけだと、スライダーで決めた半端な音量から、
  いつまでも半端な値のままになり、16 回押しても端に届かない。
- **出力先ごとの判断は、`Core/` の `OutputDevice` にまとめる**: 音量調整が有効か、扱えるか、倍率をどう決めるか、などは、
  装置の情報(Core Audio から読む)だけで決まる。判断を `Core/` に置けば、装置がなくても、テストで確かめられる。
- **装置が自分で音量を変えられるかを見分けられないときは、アプリの音量調整を有効にする**: 無効とまちがえると、
  音量を変えられない装置から、最大音量が出る。有効とまちがえた場合は、音量が二重に掛かるだけである。
- **自動で下げる量は、バンドの山の重なりを含めて見積もる**: となり合うバンドを上げると、合わせた増幅が、1つのバンドの量より
  大きくなる(本物のエンジンで測った)。見積もりの係数は、測った値から決め、エンジンのテストが、見積もりと測った値を比べ続ける。
- **音量を変えられない出力先の経路は、持ったままにする(案A)**: 出力先が変わるたびに経路を作り直すと、0.15 秒ほど、
  加工なしの音が出る。音量を変えられない出力先では、それが最大音量になる。
  持ったままにする作りは、試作のときから USB SPDIF Adapter で動いていたもので、戻した瞬間に切れ目がないことを、記録と、利用者の耳で確かめた。
  経路の数だけ、処理が動き続けるので、負荷は増える。
- **出力先に合わせる処理は、「いまの状態を読んで、あるべき形に合わせる」形で書く**: 知らせごとに「何が起きたか」を見分けて
  処理する形だと、知らせの順序や重なりで、食い違いが起きる。読み直して合わせる形なら、何度呼ばれても、同じ結果になる。
- **始められなかった出力先は、出力先の顔ぶれが変わるまで、やり直さない**: 経路を作りかけて失敗すると、集約装置を消したときの
  知らせが来る。知らせのたびにやり直すと、止まらなくなる。
- **出力装置の周波数が変わったら、経路を作り直す。前の経路の音を消し、前の経路を残したまま新しい経路を作り、できたら片付ける**:
  経路は、作ったときの周波数で動き、周波数が変わると、取り出した音に無音が混ざる。先に片付けると、作り直す間(0.7 秒ほど)、
  元の音を消すものがなくなり、加工なしの元の大きさの音が出る。前の経路を残せば、そのタップが元の音を消し続ける。
  前の経路の音を先に消すのは、2つの経路の音が重なって、元の大きさを超えないようにするため(作り直す間は、無音になる)。

## 6. 画面の言語(配布の TICKET-005)

画面は、日本語と英語。macOS の言語の設定に合わせて切り替わる。日本語でも英語でもない言語の Mac では、英語で出す。

### 作り

- コードの文言は、日本語のまま書く(利用者の判断。2026-10-26)。英語の訳は、文字列カタログ(`*.xcstrings`)に置く。
  カタログの見出しは、コードの日本語の文言そのもの。
- カタログは、部品ごとに分かれている。アプリ(`SimpleEqualizer/`)、`Core/` の `SimpleEqualizerCore`、`SimpleEqualizerEngine`、
  許可の説明文(`InfoPlist.xcstrings`)の4つ。`Core/` の文言は、`Core/` の中のカタログから引く(`bundle: .core`、`bundle: .module`)。
- SwiftUI の `Text("…")`、`Button("…")`、`.help("…")` などに文字をじかに書いた所は、SwiftUI が自動で訳す。
  `String` で渡す所(関数が返す文、`NSAlert` の文、`LabeledContent` の値など)は、`String(localized: "…")` で包む。
  包まないと訳されない。訳さない文字(目盛りの数字、`dB`、音量の数値)は `Text(verbatim:)` にして、カタログに入れない。
- 文の断片を `+` でつながない。文ごとに1つの見出しにする。英語では、語順も、文と文の間の空白も違うため。
  件数を含む英語の文は、単数と複数を書き分ける(カタログの「複数形」)。

### 言語の選ばれ方と、2つの設定

- 開発の言語(`DEVELOPMENT_LANGUAGE`、Info.plist の `CFBundleDevelopmentRegion`)を英語にしてある(`Config/Project.xcconfig`)。
  macOS は、利用者の言語に合う表がないとき、開発の言語の表を使う。これで、ほかの言語の Mac では英語になる。
  Info.plist に直接書いても、Xcode が作る値(`DEVELOPMENT_LANGUAGE` から作る)に上書きされて効かなかった。
- カタログには、日本語の値も、見出しと同じものを明示して入れてある。日本語は元の言語なので、入れなくても動きそうに見えるが、
  入れないと日本語の表(`ja.lproj/Localizable.strings`)が作られず、`Core/` の部品には `ja.lproj` 自体ができない。
  開発の言語が英語なので、日本語の Mac でも英語の表が使われるおそれがある(`failures.md` の 2026-10-26)。
  自動テスト(`StringCatalogTests`)が、どの見出しにも英語の訳と日本語の値があることを確かめる。
- `Core/` の部品(`SimpleEqualizerCore` など)の言語は、アプリが選んだ言語に従う。

### 設定のウィンドウでの選択(2026-10-27)

- 選んだ言語は、このアプリの設定の `AppleLanguages`(macOS のアプリごとの言語の指定)に書く。
  システム設定の「言語と地域」→「アプリケーション」が書くのと同じ値なので、どちらで変えても食い違わない。
  `state.json` に別に持つと、システム設定で変えたときに、2つが食い違う。
- 読むときは、このアプリの設定だけを読む(`persistentDomain(forName:)`)。`UserDefaults.standard` から読むと、
  macOS 全体の言語の一覧が返り、指定がないことと見分けられない。
- 切り替わるのは、起動し直したとき。動いている間に、全部の画面(`NSAlert`、`String(localized:)` で作った文、`Core/` の文)を
  切り替える手段は、Apple の標準の仕組みにはない。自動では起動し直さない。起動し直す間、音が加工なしの最大音量に戻るため。
- 起動したときの選択(`LanguageSetting.atLaunch`)を覚え、選択がそれと違う間だけ、起動し直すと切り替わることを知らせる。

### `Core/` の文言の持ち方

- `Core/` の文言は `LocalizedStringResource` で持ち(`PresetError.message` など)、画面に出す文(`description`)は、そこから作る。
  テストで、言語を指定して日本語と英語の両方を確かめるため。
- `swift test` では、言語を指定しないと、いつも英語になる(テストを動かすプログラムが、英語だけに対応しているため)。
  テストで文言の中身を確かめるときは、`text(_:_:)` で言語を指定する。
- 「フラット」の名前(`Preset.flatName`)と、名前を決められないときの名前(`Preset.defaultName`)も、言語で変わる。
  どの言語の「フラット」の名前も、利用者のプリセットには使わせない(`Preset.reservedNames`)。
  英語の画面で「フラット」という名前を作り、日本語に切り替えると、読み込みのときに名前が重なり、
  そのプリセットが壊れたものとして外されるため。

### 文言を足したり変えたりしたとき

1. コードに日本語で書く(上の「作り」のとおりに包む)。
2. `tools/sync-strings.sh` を動かす。ビルドして、コードの文言をカタログに足し、英語の訳か日本語の値がない見出しを出す。
   コードで使われなくなった見出しにも印がつくので、消す。
3. 出てきた見出しに、英語の訳と、日本語の値(見出しと同じ)を入れる。Xcode のカタログの画面でも、手でもよい。
4. `swift test --package-path Core` で、抜けがないことを確かめる。

## 7. ホームページ(ホームページの TICKET-003、004)

GitHub Pages に置く、紹介とダウンロードの案内のページ。載せる内容は仕様書 7.1 の「ホームページ」。

### 作り

- `site/` に、手で書いた HTML と CSS を置く。外部のライブラリ、テーマ、フォントは使わない。
  `docs/` は開発の記録に使っているので、GitHub Pages の「ブランチから公開」(直下か `docs/` だけを選べる)は使わず、GitHub Actions で公開する。
- 画像は、README と同じもの(`assets/readme/`、`assets/main_window.png`)を使う。`site/` には写さず、
  `tools/build-site.sh` が、公開するときに `assets/` へまとめて入れる。README の画像を直せば、ページにも反映される。
  ページからは `assets/...`(日本語のページからは `../assets/...`)で読む。
- ページの文言は、README の冒頭(説明、動く環境、使う前に、入れ方、許可)と同じにしている。
  README のその部分を直したら、ページの英語と日本語も直す。細かい使い方はページに写さず、README へリンクする。
- 日本語のページでは、本文の途中で改行しない(HTML の改行が、空白として出るため)。
  見出しと冒頭の文は、`word-break: auto-phrase` で、語の途中で折り返さないようにしている。

### 公開

- `.github/workflows/pages.yml` が、`main` に `site/`、`assets/`、`tools/build-site.sh` の変更が入ったとき(と手動)に、
  `tools/build-site.sh _site` でまとめて公開する。
- リポジトリの Settings → Pages で、Source を「GitHub Actions」にするまでは公開されない。
  非公開のリポジトリでは(無料のプランでは)有効にできないので、リポジトリを公開してから設定する(TICKET-005)。

### 手元で見る

```bash
tools/build-site.sh
open build/site/index.html
```

`build/` は Git に入らない。
