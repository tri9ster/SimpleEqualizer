# タップで取り出した音を AVAudioEngine に通す方法(2026-10-12)

TICKET-004 のための調査。仕様書 7章は、音の加工に `AVAudioEngine` と `AVAudioUnitEQ` を使うと決めている。
タップで取り出した音をこの部品に通す方法を、開発キット(macOS 27.0)のヘッダーで調べた。

## 1. 結論

- いまのコールバック(集約装置の入出力コールバック)をそのまま使い、その中から `AVAudioEngine` を
  「手動レンダリング(リアルタイム)」で呼ぶ方式を採る。
- 実機で確かめた結果(2026-10-12、TICKET-004): 音が出て、イコライザーが効き、遅れの違いは感じられなかった。
  設定を切り替えた瞬間にエンジンが加工を断ることは、入れる・切るの切り替えでは起きなかった(0 回)。
  音声のスレッドの負荷は約 1.2%(うちエンジンは約 0.4%)。

## 2. 方式の比較

| | 方式1: エンジンの入出力を集約装置に向ける | 方式2: 手動レンダリング(採用) |
| --- | --- | --- |
| しくみ | エンジンの入力と出力の装置を、集約装置に切り替える。コールバックはエンジンが持つ | コールバックは自分で持ち、その中でエンジンに「この音を加工して」と頼む |
| 遅れ | 入力と出力で別々にバッファを持つので、増える見込み | 増えない(同じコールバックの中で加工が終わる) |
| いまの経路 | 作り直しになる | そのまま使える。エンジンが失敗した回は、加工なしの音に切り替えられる |
| 不確かな点 | 非公開の集約装置を、エンジンの装置として指定できるか | 設定を変えた瞬間に、エンジンが加工を断る回がある(3章) |

チケットでは方式1を先に試す予定だった。方式2を先にした理由は、遅れが増えないことと、
TICKET-002・003 で動くと確かめた経路を壊さずに試せること。

## 3. ヘッダーで分かったこと

- `enableManualRenderingMode(.realtime, format:maximumFrameCount:)` で、エンジンを手動レンダリングに切り替える。
  エンジンのほかの部品に触る前に呼ぶこと、とある。
- 入力は `inputNode.setManualRenderingInputPCMFormat(_:inputBlock:)` で渡す。
  エンジンが、加工の途中でこのブロックを呼んで音を受け取る。
- 加工は `manualRenderingBlock` を、音声のスレッドから呼ぶ。
- **設定を変えた瞬間の注意**: ほかのスレッドからエンジンや部品の設定を変えると、
  その瞬間の `manualRenderingBlock` が「いまはできない」(`CannotDoInCurrentContext`)を返すことがある、とある。
  イコライザーのスライダーを動かすたびに起きるなら、音が一瞬だけ加工なしになる。
  試作では、この回数を数えて画面に出し、どのくらい起きるかを確かめる。
- **Apple の立場**: macOS 27 で足されたリアルタイム用の入力ブロック(`AVAudioIONodeInputBlockRealtimeSafe`)には、
  「Swift is not supported for use with audio realtime threads」(Swift は音声のリアルタイムのスレッドでの使用に対応していない)
  という注記がつき、Swift からは使えない。従来の入力ブロックは Swift から使える。

## 4. 作り

- エンジンの中の形式は、標準の形式(32 ビットの浮動小数点、チャンネル別)にそろえる。
  `AVAudioUnitEQ` などの加工の部品は、この形式を前提にしている。
- 取り出した音は、左右が交互に並ぶ形式である。コールバックの中で、チャンネル別に並べ替えてエンジンに渡し、
  受け取った音を交互に並べ直して出力する。並べ替えの置き場は、開始のときに確保しておく。
- 経路は「タップ → エンジン(イコライザー1バンド) → 音量 → 出力」。音量はエンジンの外で掛ける(TICKET-002 と同じ処理)。
- エンジンが加工を断った回、または形式が合わない回は、TICKET-002 の経路(加工なし、音量だけ)に切り替える。無音にはしない。

## 5. 今後の検討(TICKET-005 で判断する)

- 3章の「Apple の立場」のとおり、Swift で音声のコールバックを書くことは、Apple が勧めていない。
  この試作でも、Swift に由来するつまずきが2件あった(`failures.md` の 2026-10-12 の2件)。
  どちらも直せたが、同じ種類の問題がまた起きる可能性はある。
- 選択肢は2つ。
  - Swift のまま続ける。コールバックの書き方のルール(`CLAUDE.md`)と、機械語を調べる確認で防ぐ。
  - コールバックの部分だけを C で書く(Apple 標準の範囲で、外部ライブラリは要らない)。画面や設定は Swift のまま。
