# 試作の結果(2026-10-12)

試作(`archive/tickets/20261012_prototype/`)で分かったことのまとめ。
案A(Core Audio のプロセスタップ)のまま次の段階へ進むかを、利用者が判断するための資料。

## 1. 結論

- **案A は、この Mac と USB SPDIF Adapter の組み合わせで成り立つ。** 案B に切り替える理由は見つからなかった。
- 仕様書 7章の構成(`AVAudioEngine` と `AVAudioUnitEQ` で加工する)も成り立つ。
- 残った課題は1件(サンプリング周波数の切り替えで音がとぎれる)。ふだん行わない操作で、「停止」と「開始」で直る。
- 判断が要ることが1件あった(4章)。利用者の判断は、案A のまま段階2 へ進むこと、音声のコールバックだけ C で書くこと(2026-10-12)。

## 2. 確かめたことと結果

利用者が実機で確かめた。くわしい記録は TICKET-002〜004 にある。

| 確かめたこと | 結果 |
| --- | --- |
| 案A の API が macOS 27 と USB SPDIF Adapter で動くか(仕様書 3.3) | 動く |
| 「システム音声の録音」の許可 | 最初の「開始」でダイアログが出る。作り直しても出し直しにならない |
| 元の音が消え、加工した音だけが出るか | 出る。音量 0 で無音になる |
| 音量の変更 | なめらかに変わる。雑音や音切れはない |
| 音の遅れ(仕様書 3.3) | 動画で気にならない。装置の申告とバッファの合計は 15.8 ミリ秒(目標は 50 ミリ秒以下) |
| 停止、終了、異常終了 | どれも音が元の経路に戻る。無音のままにならない |
| スリープ | 復帰後も、設定を保ったまま動く |
| 出力先の切り替え、ケーブルの抜き差し | 「Mac miniのスピーカー」に切り替わる。戻すと、加工が同じ音量のまま続く |
| 長時間(30 分ほど)の再生 | 問題なし |
| 負荷 | 音声のスレッドは約 1.2%(エンジンを通した場合)。目標は 3% 以下 |
| `AVAudioEngine` に通せるか | 通せる。1 kHz を下げると音が変わる。遅れの違いは感じられない |
| 設定を変えた瞬間の雑音 | ない。エンジンが加工を断った回は 0 |
| サンプリング周波数の切り替え(44.1 kHz と 48 kHz) | **音がとぎれる。**「停止」と「開始」で直る |

未確認のこと:

- イコライザーのスライダーを連続して動かしたときに、エンジンが加工を断る回があるか(段階3 で確かめる)。
- サンプリング周波数の切り替えで音がとぎれる原因(段階5 で確かめる)。
- 最適化ありのビルド(Release)での負荷。測ったのは最適化なしのビルドだけ。
- SONOS Ray がネットワーク経由の命令を、光デジタル入力の再生中に受け付けるか(案C。第2段階の候補で、試作の範囲外)。

## 4. 判断が要ること: 音声のコールバックを書く言語

**決定(2026-10-12): 案2。コールバックの部分だけ C で書く。**

- 事実:
  - macOS 27 の開発キットには、「Swift は音声のリアルタイムのスレッドでの使用に対応していない」という注記がある
    (`AVAudioEngine_Tap.md` の3章)。
  - この試作で、Swift に由来するつまずきが2件あった(`failures.md`)。
    1件はアプリが落ち、1件は CPU 使用率が目標の倍以上になった。どちらもビルドでは分からなかった。
  - どちらも直せた。機械語を調べる確認の手順を作ってからは、同じ種類の誤りを、試してもらう前に2件見つけて直せた。
- 選択肢:

| | 案1: Swift のまま続ける | 案2: コールバックの部分だけ C で書く |
| --- | --- | --- |
| 内容 | いまの作りを続ける | 音声のスレッドで動く関数(数十行〜百数十行)を C で書く。画面、設定、エンジンの組み立ては Swift のまま |
| 外部ライブラリ | 不要 | 不要(Xcode の標準の範囲) |
| 利点 | 言語が1つで済む。いま動いている | 実行時の処理が裏で呼ばれることがない。Apple の勧める形に合う |
| 弱点 | 書き方のルールと、機械語を調べる確認に頼る。最適化の設定で動きが変わる | 言語が2つになる。C の部分は自動テストがしにくい(音声の部分なので、もともとテストの対象外) |

- Claude の意見: **案2 を勧める。** 理由は、音が大きく出るおそれのある部分で、「ビルドでは分からない誤り」を仕組みとして減らせること。
  C にする範囲は小さく、段階2 で音声のコードを作り直すときに、あわせて行える。
  案1 でも進められるが、コールバックを直すたびに機械語の確認が要る。

## 6. 次の段階への申し送り

- 段階2(音量): 音声のコードを作り直す。換算はテストを先に書く。4章の判断を反映する。
- 段階3(イコライザー): スライダーの連続操作で、エンジンが加工を断るかを最初に確かめる。
- 段階5(出力装置との連動): 抜き差し、出力先の切り替え、スリープは、試作でも問題なく動いた。
  処理が止まる場合が実際にあるかを先に確かめる。サンプリング周波数の切り替えの原因も、ここで調べる。
- 音声のコールバックを足したり直したりしたときは、試してもらう前に機械語を調べる(`CLAUDE.md`、`failures.md`)。
