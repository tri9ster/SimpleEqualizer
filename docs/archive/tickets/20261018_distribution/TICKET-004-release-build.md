# TICKET-004: 最適化ありのビルド(Release)

## 概要

配布するアプリは Release でビルドする。Release でも動きが変わらないこと、負荷が下がることを確かめる。

## ステータス

- [x] 作業中
- [x] 動作確認済み
- [x] 完了

## 依存関係

なし

## 現状

2026-10-18 時点。未着手。

- いままでの確認は、すべて Debug のビルドで行った。Release は一度も試していない。
- Debug では、ロックを使う実行時の処理が音声のスレッドに入って、負荷が上がったことがある(`failures.md`)。最適化で消えるはずのものが、Release でどうなるかは、確かめていない。

## 対応方針・作業手順

1. Release でビルドする(`-configuration Release`。生成物は、いつもの `DerivedData` に出す)。警告を確かめる。
2. 音声のコールバックの機械語を、`failures.md` の手順で調べる(ロックや、メインスレッドの検査が入っていないか)。
3. 利用者に、Release のアプリで、TICKET-008(段階5)の確認の一部(起動と終了、ふだんの音、出力先の切り替え、負荷)を頼む。
   **スピーカー側の音量を下げてから試す。**
4. Debug と Release で、同じ識別子のアプリが2つ macOS に登録されないかを確かめる(`failures.md` の仮のアイコンの件)。

## 実施結果

2026-10-18 に行った。コードと設定は変えていない。

### Claude が確かめたこと

- Release のビルドは、警告もエラーもなく通った。生成物は、いつもの `DerivedData` の `Release/` に出た。
- 機械語(`otool -tV`)で、音声のスレッドで動く関数(`seq_io_proc`、`seq_render`、`fill_with_silence`、
  エンジンへの入力のブロック、`seq_render_state_engine_input`)が呼ぶ先を調べた。呼ぶのは次の3つだけだった。
  - `bzero`(無音で埋める)
  - エンジンの入口(`blr`。設計どおり。`architecture.md`)
  - `__stack_chk_fail`(スタックの破損を見つけたときだけ呼ばれ、アプリを止める。コンパイラが入れる)
- メインスレッドの検査(`isCurrentExecutor`、`checkIsolated`)は、音声の関数には入っていない(画面の側にはある)。
- Debug と Release のアプリが、同じ識別子で macOS に2つ登録された。どちらもアイコンを含むので、仮のアイコンの件(`failures.md`)は起きない見込み。
  ログイン時の起動は、Debug のほうを指したまま。
- 利用者が起動したあと、動いているのが Release のほうだけであることを、プロセスの場所で確かめた。

### 利用者が確かめたこと(2026-10-18)

スピーカー側の音量を下げてから、Release のアプリで確かめ、すべて問題がなかった(個別の様子は聞いていない)。

| 番号 | 確かめること | 結果 |
| --- | --- | --- |
| 1 | 起動の瞬間(大きな音、雑音、許可を求める画面) | OK |
| 2 | ふだんの音(音量、イコライザー、ラウドネス) | OK |
| 3 | 出力先の切り替え | OK |
| 4 | 音量キーと、押したときの表示 | OK |
| 5 | 負荷 | CPU 使用率は 3% 未満 |
| 6 | 終了 | OK |

- Debug と同じ識別子と証明書なので、許可は出し直さずに済んだと見られる(許可を求める画面が出たかは、個別には聞いていない)。
- Debug との負荷の差は、測っていない(どちらも 3% 未満)。
