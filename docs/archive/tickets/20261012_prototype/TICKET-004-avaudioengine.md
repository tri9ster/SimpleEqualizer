# TICKET-004: 取り出した音を AVAudioEngine に通せるかの確認

## 概要

仕様書 7章は、音の加工に `AVAudioEngine` と `AVAudioUnitEQ` を使うと決めている。
タップで取り出した音をこの部品に通せるか、通したときに遅れがどれだけ増えるかを、段階3(イコライザー)の前に確かめる。
通せないと分かれば、イコライザーを自分で計算する方式に変える必要があり、段階3の規模が変わる。

## 対応方針・作業手順

1. `AVAudioEngine` の入出力を、TICKET-002 の集約装置に向けられるかを調べる。
   調べた内容は `docs/research/AVAudioEngine_Tap.md` に残す。
2. 向けられる場合: 経路を「タップ → `AVAudioUnitEQ`(1バンドだけ) → 音量 → 出力」に組み替える。
   TICKET-002 の経路は消さず、画面で切り替えられるようにする(聴き比べと、遅れの比較のため)。
3. 向けられない場合: 別のつなぎ方(コールバックで受けた音を `AVAudioEngine` へ渡すなど)を1つだけ試す。
   それでも通せなければ、そこで止めて結果を記録する。イコライザーを自分で計算する方式の検討は TICKET-005 で行う。
4. 確認用に、イコライザーの1バンド(1 kHz、0 dB と −10 dB の切り替え)を画面に足す。
   **増幅はしない**(リミッターがまだないため)。

### 安全のための決まり

- 音量の初期値は 30 のまま。経路を切り替えたときに音量が上がらないようにする。
- 経路を切り替える直前に、利用者に SONOS 側の音量を下げてもらう。

## 実施結果

2026-10-12 に実施。利用者が確認し、タップで取り出した音を `AVAudioEngine` に通せると分かった。

行ったこと:

- 開発キットのヘッダーを調べ、`docs/research/AVAudioEngine_Tap.md` に残した。
- **手順からの変更**: 「エンジンの入出力を集約装置に向ける」方式ではなく、
  「いまのコールバックの中から、エンジンを手動レンダリングで呼ぶ」方式を先に作った。
  遅れが増えないことと、TICKET-002・003 で動くと確かめた経路を壊さずに試せることが理由。
- 経路は「タップ → エンジン(1 kHz の1バンド) → 音量 → 出力」。`SimpleEqualizer/EngineProcessor.swift` を足した。
- 画面に、経路の切り替え(「直接」と「AVAudioEngine」)と、「1 kHz を −10 dB にする」の切り替えを足した。
  経路は、止まっている間だけ変えられる(動いている間に切り替えて、音量が変わるのを防ぐため)。
- エンジンを通せなかった回は、加工なしの音(音量だけ掛けた音)に切り替える。その回数と、最後の理由を画面に出す。

見直し(`/code-review`)で見つかり、直したこと:

- エンジンの経路で扱えない形(チャンネル別の形式、上限を超えるバッファ)でも開始していた。開始しないようにした。
  合わないまま始めると、表示は AVAudioEngine なのに、実際は加工なしの音が出続ける。
- エンジンが置き場を差し替えた場合に、古い音を読むおそれがあった。呼んだあとの場所から読むようにした。
- 「取り出した音の大きさ」を、加工のあとの音で測っていた。加工の前の音で測るようにした(直接の経路と同じ意味)。
- エンジンを通せなかった理由を捨てていた。最後の理由を残して画面に出すようにした。

見直しで見つかり、直していないこと(`TODO.md` に記載):

- イコライザーで下げている最中にエンジンを通せない回があると、その回だけ加工なしの音が出て、下げた帯域が一瞬戻る。
  無音にするよりは目立たないと考え、試作ではこのままにした。どのくらい起きるかを、今回の確認で数える。
- 動作中に装置の周波数が変わっても、エンジンを作り直さない(TICKET-003 の 9 と同じ課題)。
- 2つの経路で、倍率を掛ける処理を別々に書いている。試作のコードは段階2で作り直す。
- イコライザーをミキサー経由でつないでいる。直接つなげば1段減るが、動くことが確かな形を優先した。

機械語の確認(Claude):

- 音声のスレッドで動く関数に、スレッドの検査(`failures.md` の1件目)が入っていない。
- 同じ関数が呼ぶのは、バッファの読み書きと単純な計算だけ。確認の途中で、
  状態の比較(`==`)と `unsafelyUnwrapped` が Swift の実行時の処理を呼ぶことが分かり、書き直した。

利用者の画面の写しから分かったこと(2026-10-12):

- AVAudioEngine の経路で、エラーなく開始できた。「1 kHz を −10 dB にする」を入れた状態で動いていた。
- コールバック 8800 回のうち、エンジンを通せなかった回は 0、形式が合わなかった回も 0。
- 遅れの見積もりは 15.8 ミリ秒で、直接の経路と同じ(エンジンは同じコールバックの中で動くので、申告される値は変わらない)。
- CPU 使用率は 3.8%(最適化なしのビルド。目標は 3% 以下)。
  動いているアプリを `sample` コマンドで5秒間調べると、内訳は次のとおりだった。
  - 音声のスレッド: 約 1.2%(うちエンジンの加工が約 0.4%、並べ替えと音量が約 0.4%)。
  - メインスレッド: 約 4%。ほぼすべて、試作の画面の書き直し(0.5 秒ごとの値の更新)。
  - 音声の処理は軽く、目標を超えた分は試作の確認用の画面によるもの。
    本番はメニューバー常駐で、ふだんは画面を出さないので、この分はかからない見込み(未確認)。試作では直さない。

利用者が確かめたこと(2026-10-12):

- 音は正常に出た。音切れや雑音はなかった。
- 「1 kHz を −10 dB にする」を切り替えると、音が変わった。切り替えた瞬間の雑音はなかった。
- 切り替えを何度か操作しても、「エンジンを通せなかった回数」は 0 のままだった。
  ヘッダーが注意している「設定を変えた瞬間にエンジンが加工を断る」ことは、この操作では起きなかった。
- 2つの経路で、音のずれの違いはなかった。
- スリープすると音は消える(ふだんどおりの動作)。復帰後に再生すると、設定が保たれたまま正常に音が出た。
