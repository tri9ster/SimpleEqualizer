# TICKET-002: タップで音を取り出し、音量を変えて出力へ流す

## 概要

システムの音をタップで取り出し、元の音を消し、音量を下げた音を USB SPDIF Adapter へ流す。
案A が成り立つかを確かめるための、いちばん単純な経路を作る。イコライザーなどの加工は入れない。

- USB SPDIF Adapter は 48 kHz / 24 ビット / 2ch で動いている。バッファは 512 フレーム。

## 対応方針・作業手順

### 経路

```
各アプリの音 → タップ(元の音は消す) → 音量 → USB SPDIF Adapter → SONOS Ray
```

`AVAudioEngine` は使わない。集約装置の入出力コールバックの中で、入力を出力へ写しながら音量を掛ける。
部品を減らし、動かないときに原因を切り分けやすくするため。`AVAudioEngine` は TICKET-004 で確かめる。

### 手順

1. 出力装置を名前(「USB SPDIF Adapter」)で探し、装置の UID を得る。見つからなければ、何もせず画面に表示する。
2. タップの設定(`CATapDescription`)を作る。
   - 自分自身のプロセスを対象から外す(外さないと音が循環する)。
   - 元の音を消す設定は `CATapMutedWhenTapped` にする。アプリが読み取っている間だけ元の音が消えるので、
     アプリが止まったときに無音のままにならない見込み。
   - 対象を USB SPDIF Adapter に出ている音だけに絞れるか(装置を指定する作り方があるか)を、
     着手時に開発キットのヘッダーで確かめる。絞れなければシステム全体を対象にし、その旨を記録する。
3. `AudioHardwareCreateProcessTap` でタップを作る。
4. 集約装置を作る。USB SPDIF Adapter を出力に、タップを入力に入れる。ほかのアプリから見えない設定にする。
5. 集約装置に入出力コールバックを登録し、開始する。
   - コールバックの中では、メモリの確保、ロック、ログ出力、ファイル操作をしない。
   - 入力と出力のチャンネル数や形式が合わないときは、無音を出す(雑音を出さない)。
6. 停止のとき、コールバック、集約装置、タップの順に片付ける。アプリの終了時にも同じ片付けをする。
7. 画面(ウィンドウ1つ):
   - 「開始」「停止」のボタン。**起動しただけでは音声に触らない。**
   - 音量スライダー(0〜100)。
   - 状態の表示(止まっている、動いている、エラーの内容)。
   - 取り出し側と出力側の形式、バッファの大きさ、装置が申告している遅れ(遅れの見積もりに使う)。

### 安全のための決まり

- 音量の初期値は 30(仕様書 4.1 と同じ)。保存はしないので、起動のたびに 30 に戻る。
- 音量は元の音量を超えない(倍率の上限は 1.0)。
- 音量から倍率への換算は、試作では仮の式(対数)を使う。正式な換算は、段階2でテストを先に書いて作る。
- 「停止」やアプリの終了で、音は加工なしの元の状態(最大音量)に戻る。画面にその注意を出す。
- Claude はビルドだけを行い、アプリの「開始」は押さない。音を出す確認は TICKET-003 で利用者が行う。

## 実施結果

2026-10-12 に実施。利用者が、音が出ることと、音量が変わることを確かめた。

行ったこと:

- `SimpleEqualizer/AudioPassthrough.swift`(経路)、`PrototypeModel.swift`(画面の状態)を足し、画面を作り直した。
- タップの対象は、USB SPDIF Adapter に出ている音だけに絞れた(`CATapDescription` に、装置を指定する作り方があった)。
  ほかの装置に出ている音には触らない。
- 手順からの変更点:
  - 集約装置の「タップの自動開始」は使わなかった。使うと、音が流れ始めるまで開始の呼び出しが待たされるため。
  - 画面に、取り出した音の大きさ、コールバックの回数、形式が合わなかった回数を足した。
    音が出ないときに、取り出せていないのか、出力できていないのかを見分けるため。
  - ウィンドウを閉じたらアプリも終わるようにした(画面なしで音声を加工し続けないため)。

見直し(`/code-review`)で見つかり、直したこと:

- 集約装置の入力に、出力装置が持つ入力がタップより前に並ぶ場合を考えていなかった。入力の後ろから使うようにした。
- 取り出した音の形式を確かめていなかった。32 ビットの浮動小数点でなければ開始しないようにした。
- 自分のプロセスを対象から外せないときも開始していた。開始しないようにした(音が循環するため)。
- 同じ名前の装置が複数あるとき、最初の1台を使っていた。開始しないようにした。
- 停止のとき、倍率を 0 に下げずに止めていた。下げてから止めるようにした。
- 音を出せなかった回でも倍率を進めていた。進めないようにした(開始時に 0 からなめらかに上げるため)。
- 回数の表示が、開始のたびに 0 に戻っていなかった。戻すようにした。
- 画面の更新用のタイマーが、止まっている間も動いていた。動いている間だけにした。

見直しで見つかり、直していないこと(`TODO.md` に記載):

- 動作中に装置が止まったとき(抜き差し、出力先の切り替え、スリープ)に、自動で止めたり再開したりしない。
  段階5(出力装置との連動)の範囲。試作では、コールバックが止まったことを検知して画面に赤字で知らせるだけにした。

利用者の1回目の確認で分かったこと(2026-10-12):

- 起動しただけでは、音はこれまでどおり出た。
- 「開始」を押すとアプリが落ちた。音は元の経路で出たままだった。
- 原因は、音声のコールバックがメインスレッド専用とみなされていたこと。直した(`docs/failures.md` の 2026-10-12)。

確認できたこと(Claude):

- `xcodebuild` のビルドが成功した(警告なし)。
- 直したあとの機械語に、コールバックの中のスレッド検査が残っていない。

利用者の2回目の確認で分かったこと(2026-10-12、直したあと):

- 「開始」を押しても落ちず、音が出た。音量スライダーで音の大きさが変わった。「停止」もできた。
- 「システム音声の録音」の許可ダイアログは、1回目の「開始」のときに出た。
  作り直したあとの2回目では、許可を出し直さずに動いた(署名が変わらないことの効果)。
- 画面に出た値:

  | 項目 | 値 |
  | --- | --- |
  | 取り出した音の形式 | 48000 Hz / 2ch / 32 ビット 浮動小数点 / 交互 |
  | 出力装置の周波数 | 48000 Hz |
  | 集約装置の入力 / 出力の数 | 1 / 1 |
  | バッファ | 512 フレーム |
  | 申告された遅れ(入力 / 出力) | 148 / 100 フレーム |
  | 遅れの見積もり | 15.8 ミリ秒 |
  | 形式が合わなかった回数 | 0(コールバック 6655 回のうち) |

- 集約装置の入力は1つだけだった。USB SPDIF Adapter は入力を持たず、入力はタップだけになる。
- 遅れの見積もり 15.8 ミリ秒は、装置が申告している値とバッファの合計である。
  再生するアプリ側と SONOS 側の遅れは含まない。聞こえ方としての遅れは TICKET-003 で確かめる。
