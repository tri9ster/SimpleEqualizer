# TICKET-003: 音声の経路の作り直し(コールバックを C へ)

## 概要

試作の音声のコード(`AudioPassthrough.swift`)を、本番の形に作り直す。

## 対応方針・作業手順

### 分け方

| 部分 | 言語 | 内容 |
| --- | --- | --- |
| コールバック | C | 入力を出力へ写しながら倍率を掛ける。倍率をなめらかに変える。回数や音の大きさを記録する |
| 受け渡しの値 | C | 画面とコールバックの間の値(倍率など)。ロックを使わない方法(C のアトミック)で受け渡す |
| 組み立て | Swift | 装置を探す、タップと集約装置を作る、コールバックを登録する、片付ける |

- C のコールバックには、段階3 でエンジン(加工)を呼ぶための口だけを用意しておく。この段階では使わない。
- 消音は、倍率 0 として扱う。切り替えは、音量と同じく、なめらかに変える。

### 手順

1. Xcode のプロジェクトに C のファイルを足し、Swift から呼べるようにする(ブリッジ用のヘッダー)。
   外部ライブラリは使わない。やり方は、着手時に小さく試してから決める。
2. C でコールバックと受け渡しの値を書く。試作の `render` と同じ動きにする。
   - 形式が合わないときは無音を出す。音を出せなかった回は倍率を進めない。
   - メモリの確保、ロック、ログ出力、ファイル操作をしない。
3. Swift の組み立てを、試作から作り直す。開始しない条件は試作と同じ
   (装置が見つからない、同じ名前の装置が複数ある、自分のプロセスを外せない、形式が違う)。
4. 試作の画面を、新しい経路につなぎ替える。経路の切り替え(「直接」と「AVAudioEngine」)は画面から外す。
5. 試作のコードを片付ける。
   - `AudioPassthrough.swift` は消す。
   - `EngineProcessor.swift` は、段階3 の参考として `docs/archive/` に写し、アプリからは外す。
6. 機械語を調べ、コールバックが C の関数だけで動いていることを確かめる。

### 安全のための決まり

- 倍率の上限は 1.0。開始のときは 0 からなめらかに上げる。
- 作り直しの前後で、同じ音量の数値に対する音の大きさが大きくならないこと(換算は TICKET-001 のものを使う)。
- Claude はビルドまでを行い、音を出す確認は利用者に頼む。

## 実施結果

2026-10-12 に実施。利用者が、作り直した経路で音が出ることを確かめた。

行ったこと:

- 音声のスレッドで動く関数を C で書いた(`Core/Sources/SimpleEqualizerAudio/`)。
  Core Audio には、C の関数(`seq_io_proc`)を直接登録する。Swift のコードは、音声のスレッドでは動かない。
- Swift の組み立てを `SimpleEqualizer/AudioPath.swift` として作り直した。
- 試作の画面は残し、新しい経路につなぎ替えた。経路の切り替えと「1 kHz を −10 dB」は画面から外した。
- 手順からの変更点:
  - **C のコードは、アプリの中ではなく `Core/` パッケージに置いた。**
    ブリッジ用のヘッダーが要らず、コールバックの計算を、音を出さずに自動テストで確かめられる。
  - **コールバックの計算にもテストを書いた(27 件)。** 音声の部分は「テストを先に書く」の対象外だが、
    入力と出力を数値で渡せば確かめられるので、テストを先に書いて作った。
  - 試作の `AudioPassthrough.swift` は、消さずに `docs/archive/20261012_prototype/` へ移した(`EngineProcessor.swift` も同じ)。
    段階3 でエンジンの経路を作り直すときの参考にするため。
  - 段階3 でエンジンを呼ぶための口は、用意しなかった。使わないコードを先に入れないため。段階3 で足す。
- 止めるときの「音をなめらかに消す」処理を、C の側に持たせた。目標の倍率を書き換えずに済む。
  消えきったことを確かめてから止める(待つ時間の上限は 0.3 秒)。

テストの記録:

- 1回目: 21 件のテストを先に書き、仮の実装で失敗を確かめた(54 件の不一致)。実装して、すべて通った。
- 2回目(見直しのあと): テストを 6 件足し、失敗を確かめた(13 件の不一致)。実装して、27 件すべてが通った。

見直し(`/code-review`)で見つかり、直したこと:

- 数でない値や無限大のサンプルが来ると、倍率 0 でも雑音として出るおそれがあった。無音に置き換えるようにした。
- 出力が複数本の装置では、タップではない入力(マイクなど)を出力へ写すおそれがあった。
  入力(タップ)と出力がそれぞれ1本の装置でなければ、開始しないようにした。
- 止めるときの待ちが 0.05 秒の固定で、バッファが大きい装置では音が消える前に止めていた。消えきるのを待つようにした。
- 目標の倍率を Swift と C の2か所で持っていた。C の側だけにした。
- 状態を捨てる処理がなかった。動いたまま捨てられた場合も、片付けてから捨てるようにした。
- 開始の直後に、「処理が止まっている」の表示が一瞬出るおそれがあった。開始後の1回目は判定しないようにした。
- 一部だけ形が合わない場合と、大きさが端数の場合の動きを、テストに書いた。

確認できたこと(Claude):

- テストが通る(音声に触らない処理 37 件、コールバックの計算 27 件)。アプリのビルドが通る(警告なし)。
- 機械語を調べ、音声のスレッドで動く関数は C の関数だけで、呼び出し先は `memset` だけだった。

利用者が確かめたこと(2026-10-12):

- 「開始」で音が出た。音量スライダーで音の大きさが変わった。
- 音量 0 で無音になった。
- 「停止」と終了で、音が元の経路に戻った。
- CPU 使用率は 1.8%(最適化なしのビルド)。試作の同じ経路(2.4%)より下がった。
