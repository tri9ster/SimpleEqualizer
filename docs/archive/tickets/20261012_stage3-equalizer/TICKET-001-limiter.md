## 概要

## 対応方針・作業手順

### リミッターの動き

- 見るのは、音量を掛けたあとの音。フレームごとに、全チャンネルの中でいちばん大きい値を調べる。
- その値が上限を超えるときは、すぐに全体の倍率を下げ、ちょうど上限に収める(左右は同じ倍率にする。音の位置を動かさないため)。
- 超えなくなったら、倍率をゆっくり 1 に戻す(0.1 秒で、下げた分の約 63% が戻る速さ。急に戻すと音が揺れて聞こえる)。
- 上限は、フルスケールちょうど(1.0)。はじめは「わずかに下(−0.1 dB)」としていたが、実装のときに変えた(実施結果)。
- 下げる倍率には下限(−40 dB)を置く。それでも収まらない分は、次の切り落としに任せる。
- 最後に、念のため、すべてのサンプルを ±1.0 の範囲に切り落とす(計算の誤差や、想定していない入力への備え)。
- リミッターが働いた回数を数え、画面から読めるようにする(TICKET-004 で表示に使う)。

### 手順

1. 失敗するテストを先に書く(`Core/Tests/SimpleEqualizerAudioTests/`)。
   - 上限を超えない入力は、そのまま出る(1サンプルも変わらない)。
   - 上限を超える入力は、出力が上限以下になる。左右の比は変わらない。
   - 超えたあと、小さい音が続くと、倍率が 1 に戻る。戻る途中の値は、だんだん大きくなる。
   - 大きな値(たとえば 100.0)、数でない値、無限大を入れても、出力は ±1.0 に収まり、数でない値にならない。
   - 働いた回数が数えられる。
   - サンプリング周波数が変わっても、戻る時間がほぼ同じである。
2. 失敗することを確かめてから、C で実装する。`seq_render` の最後に入れる。
   - 戻す速さはサンプリング周波数で決まるので、開始のときに周波数を渡す関数を足す。
   - メモリの確保、ロック、ログ出力、ファイル操作をしない。
3. `AudioPath.swift` から、開始のときに周波数を渡す。
4. テストが通ること、ビルドが通ることを確かめる。

### 安全のための決まり

- この時点では増幅がないので、リミッターは働かない。作り直しの前後で、音が変わらないこと。
- 倍率の上限(1.0)と、開始のときに 0 から上げる動きは変えない。

Claude が確かめたこと:

- テストを先に書き、実装の前に失敗することを確かめた。実装のあと、テストは 101 件(55 + 46)が通った。ビルドも通った。
- 機械語を調べた。音声のスレッドで動く関数(`seq_io_proc`、`seq_render`、`apply_limiter`)が呼ぶのは、
  自分の C の関数と `memset` だけだった。

チケットから変えたこと:

- **上限を、−0.1 dB ではなく、フルスケールちょうど(1.0)にした。**
  −0.1 dB にすると、増幅していなくても、フルスケールまで使っている音源(多くの音楽)でリミッターが働き、
  元の音がわずかに変わる。段階2 のテスト(フルスケールの音が、音量 100 でそのまま出る)が失敗して気づいた。
- 戻す速さは、0.1 秒で約 63% 戻る形にした(0.2 秒で約 86%)。聴いて合わなければ、TICKET-004 の確認で変える。

`/code-review` の指摘と対処:

| 指摘 | 対処 |
| --- | --- |
| 壊れた大きな値が1サンプル混ざると、倍率がほぼ 0 まで落ち、しばらく無音になる | 下げる倍率に下限(−40 dB)を置いた。テストを足した |
| 働く必要のない回(ほとんどの回)でも、出力をもう1回読んでいる | 音量を掛けるループの中で出力の最大値を求め、上限以下で、倍率も戻りきっている回は通さない |
| リミッターに渡す周波数が、取り出した音の形式の値だった | 出力装置の周波数を使う(読めないときだけ、形式の値) |
| チャンネル別の複数本のテストがない | テストを足した(同じ倍率で下がる、長さが違っても範囲の外に触らない) |
| テスト用の入れ物が重複している | 段階2 のテストの入れ物を共用にした |
| 回数は「上限を超えた回数」ではなく「抑えていた回の数」 | そのままにし、ヘッダーの説明を直した(TICKET-004 の「抑えている間だけ表示する」に合う) |
| 動作中に出力装置の周波数が変わると、戻る時間がずれる | 直さない。周波数の切り替えは段階5 の課題(`docs/TODO.md`)で、経路を作り直すときに渡し直す |
