# TICKET-003: コールバックからエンジンを呼ぶ

## 概要

C のコールバックの中から、`AVAudioEngine`(手動レンダリング)を呼ぶ形にする。
エンジンの中には、イコライザー(10 バンド)と、ラウドネス用のフィルター(低音と高音の2つ)を組む。
このチケットでは、イコライザーはすべて 0 dB、ラウドネスは切のまま通し、**音が変わらないこと**を確かめる。
設定を変える画面は TICKET-004 で作る。

## 対応方針・作業手順

### 経路

```
タップ → [C のコールバック] 並べ替え → エンジン(イコライザー → ラウドネス) → 並べ直し → 音量 → リミッター → 出力
```

### 分け方

| 部分 | 言語 | 内容 |
| --- | --- | --- |
| エンジンの組み立てと設定 | Swift | 手動レンダリングに切り替える。イコライザーとラウドネスのフィルターをつなぐ。値を設定する。片付ける |
| エンジンを呼ぶところ | C | 取り出した音(左右が交互)をチャンネル別に並べ替え、エンジンを呼び、受け取った音を交互に並べ直す |
| 並べ替えの置き場 | C | 開始のときに確保し、コールバックの中では確保しない |

- エンジンを呼ぶ入口(ブロック)は、開始の前に C の側へ渡し、コールバックを止めたあとに外す。動いている間は差し替えない。
- エンジンが音を受け取るときに呼ぶブロックも、C で作る(音声のスレッドで Swift を動かさない)。
- Swift と C の間でブロックを受け渡すやり方(型の合わせ方)は、着手時に小さく試してから決める。
  テストで、にせのブロックを渡して、並べ替えと受け渡しが正しいことを確かめる。

### エンジンの中身

- イコライザー: `AVAudioUnitEQ`、10 バンド。種類はどのバンドも同じ(山形に上げ下げするフィルター)、幅は 1 オクターブ。
  はじめはすべて 0 dB。
- ラウドネス: 別の `AVAudioUnitEQ`、2 バンド(低音は 100 Hz より下、高音は 8 kHz より上を上げ下げするフィルター)。
  はじめは 0 dB。
- つなぎ方: 試作ではミキサーを経由した。ミキサーを通さずに直接出力へつなげるかを確かめ、つなげるなら直接つなぐ。

### エンジンを通せなかったとき

- 次の場合は、その回だけ、エンジンを通さない音(取り出した音そのまま)に切り替える。そのあと、音量とリミッターを掛ける。
  - エンジンが加工を断った。
  - 1回のフレーム数が、置き場の大きさ(4096)を超えた。
  - チャンネル数が、開始のときと違う。
- 断られた回数を数え、画面から読めるようにする。
- 無音にしない理由: 設定を変えた瞬間に、音がとぎれて聞こえるため。
  エンジンを通さない音は、イコライザーで下げていた帯域が元に戻るが、音量とリミッターは掛かるので、上限は超えない。

### 手順

1. テストを先に書く(並べ替え、並べ直し、にせのブロックでの受け渡し、通せなかったときの切り替え、回数)。
2. C で、エンジンを呼ぶ処理を書く。
3. Swift で、エンジンの組み立てを、試作のコードを参考に作り直す(10 バンド + 2 バンド)。
4. `AudioPath.swift` の開始と停止に、エンジンの組み立てと片付けを入れる。順序は、
   開始: エンジンを作る → C へ渡す → コールバックを始める。停止: 音を消す → コールバックを止める → C から外す → エンジンを止める。
5. 機械語を調べ、音声のスレッドで動く自分のコードが C の関数だけであることを確かめる(`docs/failures.md` の手順)。

### 安全のための決まり

- このチケットでは、どのバンドも 0 dB から動かさない(動かす画面がない)。
- 開始しない条件を足す: エンジンを作れなかったときは、音声に触らず、理由をポップアップに出す。

### チケットから変えたこと

- **つなぐところだけ、Objective-C で書いた。** チケットでは「Swift と C の間でブロックを受け渡す」としていた。
  Swift から渡すと、Swift のクロージャが間に入り、音声のスレッドで Swift のコードが動く。
  Objective-C なら、エンジンの入口をそのまま C に渡せる。Xcode の標準の範囲で、外部ライブラリは使っていない。
  あわせて、macOS 27 で足された、音声のスレッド向けの入力の入口(Swift からは使えない)を使えた。
  音声のスレッドで動く Objective-C のコードは、C の関数を1つ呼ぶだけのブロック1つである。
- **エンジンの組み立てを、アプリの側ではなく `Core/` パッケージに置いた。** 手動レンダリングのエンジンは装置に触らないので、
  音を出さずに自動テストで確かめられる。本物のエンジンを C のコールバックにつないだ形で、次を確かめた。
  - すべて 0 dB のとき、どの高さの音も大きさが変わらない(40 Hz〜15 kHz で、ずれは 0.1 dB 未満)。左右が混ざらない。
  - 1 kHz を 10 dB 下げる・上げると、1 kHz の音が約 10 dB 変わり、離れた高さの音は変わらない。
  - 上げた結果がフルスケールを超えると、リミッターが抑える。
  - ラウドネスの補正は、低音と高音だけを持ち上げる。イコライザーを切にしても効く。
  - 44.1 kHz でも動く。
- **エンジンの中は、ミキサーを通さず、直接出力へつないだ**(試作からの申し送り)。つなげることを、上のテストで確かめた。
- **`Core/` パッケージの対象を、macOS 15 から macOS 27(アプリと同じ)に上げた。** 部品をつなぐ関数に、macOS 27 のものを使うため。
- イコライザーとラウドネスの値を設定する関数は、エンジンの側に作ってある。アプリからは、まだ呼んでいない(TICKET-004、005)。

### Claude が確かめたこと

- テストは 167 件(88 + 65 + 14)が通った。アプリのビルドも通った。
- 機械語を調べた。音声のスレッドで動く関数(`seq_io_proc`、`seq_render`、`render_through_engine`、`apply_limiter`、
  入力のブロック)が呼ぶのは、自分の C の関数、`memset`、エンジンの入口だけだった。スレッドの検査は入っていない。
- **エンジンが加工を断る回数(試作からの申し送り)**: 別のスレッドからイコライザーとラウドネスの値を休みなく変えながら、
  2000 回ぶんの音を通すテストで、断られた回は 0 だった。実機でスライダーを動かしたときの回数は、TICKET-004 で確かめる。
